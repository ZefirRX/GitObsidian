# Умные указатели

> [!abstract] О чём заметка
> **Умный указатель** (smart pointer) — объект-обёртка над обычным указателем, который сам освобождает память, когда она больше не нужна. Это идиома RAII, применённая к динамической памяти: она избавляет от забытых `delete`, утечек при исключениях и двойного освобождения. Заметка разбирает `unique_ptr`, `shared_ptr`, `weak_ptr` и объясняет, какой из них выбрать.

## Зачем это нужно

Посмотрим на типичный «сырой» код:

```cpp
int some_func() {
    int* my_data = new int[600];
    if (some_condition) {
        // что-то делаем
        return 1;                  // утечка: delete[] не вызван
    }
    // работаем дальше
    if (another_condition) {
        test_func();               // а если здесь исключение? тоже утечка
        return 2;
    }
    delete[] my_data;
    return 0;
}
```

Недостатков два:

- на каждом выходе из функции пришлось бы писать `delete[]` — это дублирование кода (и его легко забыть);
- если внутри `test_func` возникнет исключение, управление до `delete[]` вообще не дойдёт — память утечёт.

Нужен объект, который **самостоятельно заботится о высвобождении своих ресурсов**: деструктор объекта на стеке выполнится при любом выходе из блока. Это и есть [[02 Жизненный цикл объекта и RAII]]; умные указатели — готовая реализация RAII для памяти в куче. Про сами указатели и `new`/`delete` см. [[08 Указатели и динамическая память]].

## Виды умных указателей

В заголовке `<memory>` определены:

| Класс | Идея | Статус |
|---|---|---|
| `std::auto_ptr` | старый умный указатель с «разрушающим копированием» | **не использовать**, удалён из стандарта в C++17 |
| `std::unique_ptr` | уникальное владение объектом | основной выбор по умолчанию |
| `std::shared_ptr` | совместное владение объектом | когда владельцев несколько |
| `std::weak_ptr` | наблюдатель без владения; решает проблемы `shared_ptr` | вспомогательный |

### Почему удалили `auto_ptr`

```cpp
std::auto_ptr<int> object1(new int(10));
std::auto_ptr<int> object2(new int(5));
object1 = object2;   // «разрушающее копирование»
```

В последней строке владение передаётся от `object2` к `object1`, а `object2` становится пустым. Присваивание, которое портит правую часть, — неожиданное поведение: такой указатель нельзя безопасно положить в контейнер или передать по значению. На замену ввели `unique_ptr`, где передача владения всегда явная (через `std::move`). Появление `auto_ptr` стало возможно только до появления move-семантики — см. [[04 Move-семантика]].

## std::unique_ptr

**`std::unique_ptr`** воплощает семантику **уникального владения**: у базового указателя ровно один владелец, копирование запрещено, доступна только передача владения.

Сравните ручной и умный варианты:

```cpp
void use_raw_pointer() {
    my_class* ptr = new my_class();
    // использование сырого указателя — потенциальные утечки
    delete ptr;                       // не забываем удалить
}

void use_unique_pointer() {
    std::unique_ptr<my_class> ptr(new my_class());
    auto field_value = ptr->field1;   // обращение как к обычному указателю
}   // ptr автоматически удалится здесь
```

Работать с `unique_ptr` можно как с обычным указателем: доступны разыменование `*ptr` и доступ к полям `ptr->field`.

### Создание

Есть два способа.

1. Через конструктор: `std::unique_ptr<my_class> ptr(new my_class("string data", 1));`
2. Через функцию `std::make_unique<T>(...)` (C++14):

```cpp
auto ptr = std::make_unique<my_class>("string data", 1);
```

Второй вариант предпочтителен: он красивее с точки зрения современного C++ (в коде нет оператора `new`) и безопаснее с точки зрения гарантий при исключениях. Но он подходит не всегда — например, когда нужен собственный **делитер** (deleter), то есть своя функция освобождения ресурса.

`unique_ptr` умеет работать и с массивами:

```cpp
auto arr = std::make_unique<int[]>(3);   // значения обнулены
arr[0] = 10; arr[2] = 30;
```

### Передача владения

Копировать `unique_ptr` нельзя, можно только **передавать владение** с помощью `std::move`.

```cpp
#include <iostream>
#include <memory>
#include <string>

struct my_class {
    std::string name;
    explicit my_class(std::string n) : name(std::move(n)) { std::cout << "+" << name << "\n"; }
    ~my_class() { std::cout << "-" << name << "\n"; }
};

void take_ownership(std::unique_ptr<my_class> p) {
    std::cout << "функция владеет " << p->name << "\n";
}   // p уничтожается здесь вместе с объектом

int main() {
    auto ptr1 = std::make_unique<my_class>("A");
    auto ptr2 = std::make_unique<my_class>("B");
    // ptr1 = ptr2;                 // не скомпилируется: копирование запрещено
    ptr1 = std::move(ptr2);         // A удаляется, ptr1 теперь владеет B
    std::cout << "ptr2 пуст: " << std::boolalpha << (ptr2 == nullptr) << "\n";
    take_ownership(std::move(ptr1));
    std::cout << "ptr1 пуст: " << (!ptr1) << "\n";
}
// Вывод:
// +A
// +B
// -A
// ptr2 пуст: true
// функция владеет B
// -B
// ptr1 пуст: true
```

После `std::move(ptr2)` объект `ptr2` пуст, а ресурсы, принадлежавшие `ptr1` (объект `A`), освобождаются сразу при присваивании. Для передачи в функцию тоже нужен `std::move`: `take_ownership(std::move(ptr1))`.

### Методы

| Метод | Описание |
|---|---|
| `get()` | возвращает сырой указатель, владение сохраняется |
| `release()` | возвращает сырой указатель и **отдаёт владение** (удалять придётся вручную) |
| `reset()` / `reset(p)` | удаляет текущий объект и (необязательно) берёт новый |
| `swap(other)` | обменивает управляемые объекты |

```cpp
auto p = std::make_unique<my_class>("C");
my_class* raw = p.release();       // p теперь пуст, delete — на нас
delete raw;
p.reset(new my_class("D"));        // p владеет D
p.reset();                         // D удаляется
```

### Полиморфизм

`unique_ptr` на базовый класс может хранить объект-наследник (см. [[05 Наследование и полиморфизм]]):

```cpp
#include <iostream>
#include <memory>

class base {
public:
    base() { std::cout << "base constructor\n"; }
    virtual ~base() = default;       // виртуальный деструктор обязателен
    virtual void func() { std::cout << "func in base class\n"; }
};

struct derived : public base {
    derived() { std::cout << "derived constructor\n"; }
    void func() override { std::cout << "func in derived class\n"; }
};

int main() {
    std::unique_ptr<base> ptr = std::make_unique<derived>();  // наследник в указателе на базовый
    ptr->func();
}
// Вывод:
// base constructor
// derived constructor
// func in derived class
```

> [!warning] Один сырой указатель — один умный
> ```cpp
> some_class* obj = new some_class();
> std::unique_ptr<some_class> ptr1(obj);
> std::unique_ptr<some_class> ptr2(obj);   // оба попытаются удалить obj
> ```
> Оба указателя вызовут `delete` для одного и того же объекта — **неопределённое поведение** (двойное освобождение; AddressSanitizer сообщает `attempting double-free`). По той же причине не вызывайте `delete` для адреса, которым уже владеет умный указатель. Создавайте умный указатель сразу из `make_unique`, чтобы сырого `obj` просто не существовало.

## std::shared_ptr

**`std::shared_ptr`** воплощает семантику **совместного владения**: все указатели на объект «сотрудничают», чтобы объект был уничтожен именно в тот момент, когда он перестал быть нужным — когда исчез последний владелец.

### Как это работает

Нужен **счётчик ссылок** (reference counter): он растёт, когда создаётся ещё один владелец, и уменьшается, когда владелец исчезает. Когда счётчик доходит до нуля, объект удаляется. Счётчик и прочая служебная информация лежат в **контрольном блоке** (control block). Сам `shared_ptr` хранит два указателя: на управляемый объект и на контрольный блок.

```text
shared_ptr A ──┐                 ┌──────────────────┐
               ├──> контрольный ─┤ счётчик ссылок: 3│
shared_ptr B ──┤       блок      │ ...              │
               │                 └──────────────────┘
shared_ptr C ──┴──> объект
```

> [!example] Почему счётчик не хранится прямо в `shared_ptr`?
> Потому что `shared_ptr` копируют, а исходный указатель может «умереть» раньше копий — тогда счётчик, лежавший в нём, пропал бы. Контрольный блок общий и живёт, пока есть хотя бы один владелец (или наблюдатель — см. `weak_ptr`).

### Создание

```cpp
std::shared_ptr<my_class> ptr(new my_class("string data", 1));   // через конструктор
auto ptr2 = std::make_shared<my_class>("string data", 1);        // предпочтительно
```

`make_shared` предпочтительнее по тем же причинам, что и `make_unique`; кроме того, он выделяет объект и контрольный блок одним куском памяти.

### Подсчёт ссылок на примере

```cpp
#include <iostream>
#include <memory>

struct base { ~base() { std::cout << "base destroyed\n"; } };

int main() {
    auto ptr = std::make_shared<base>();       // счётчик = 1
    std::cout << ptr.use_count() << "\n";      // Вывод: 1
    {
        auto ptr1 = ptr;                       // счётчик = 2
        std::cout << ptr.use_count() << "\n";  // Вывод: 2
    }                                          // ptr1 умер, счётчик = 1
    std::cout << ptr.use_count() << "\n";      // Вывод: 1
}   // ptr умер, счётчик = 0 -> «base destroyed»
```

Методы `shared_ptr`:

| Метод | Описание |
|---|---|
| `use_count()` | количество `shared_ptr`, ссылающихся на один и тот же объект |
| `reset()` | отпускает объект (счётчик уменьшается), заменяет его на новый |
| `swap(other)` | обменивает управляемые объекты |
| `get()` | сырой указатель на объект |

> [!warning] Двойное владение из одного сырого указателя
> ```cpp
> some_class* obj = new some_class();
> auto ptr = std::shared_ptr<some_class>(obj);
> {
>     auto ptr1 = std::shared_ptr<some_class>(obj);   // второй контрольный блок!
> }   // ptr1 удаляет obj, потом ptr удалит его ещё раз
> ```
> Два `shared_ptr`, созданные из одного сырого указателя, имеют **разные** контрольные блоки и не знают друг о друге. Копии нужно делать только из существующего `shared_ptr`: `auto ptr1 = ptr;`. Если объекту нужно получить `shared_ptr` на самого себя, используют `std::enable_shared_from_this`.

## std::weak_ptr

### Проблема: циклические ссылки

`shared_ptr` не справляется с **циклической зависимостью**. Простейший пример — объект, который держит `shared_ptr` на самого себя:

```cpp
#include <iostream>
#include <memory>

struct test_class {
    std::shared_ptr<test_class> m_ptr;
    ~test_class() { std::cout << "destructor called\n"; }
};

int main() {
    {
        auto ptr = std::make_shared<test_class>();
        ptr->m_ptr = ptr;
        std::cout << ptr.use_count() << "\n";   // Вывод: 2 — ptr и m_ptr
    }   // ptr умер: счётчик = 1 (держит m_ptr), деструктор НЕ вызван, память утекла
}
```

Объект владеет сам собой, поэтому счётчик никогда не дойдёт до нуля. То же происходит, если два объекта ссылаются друг на друга:

```cpp
struct node {
    int m_value;
    std::shared_ptr<node> parent;
    node(int value) : m_value{value} {}
    ~node() { std::cout << "destructor called\n"; }
};

{
    auto node1 = std::make_shared<node>(1);   // 1 ссылка на node1
    auto node2 = std::make_shared<node>(2);   // 1 ссылка на node2
    node1->parent = node2;                    // 2 ссылки на node2
    node2->parent = node1;                    // 2 ссылки на node1
}   // оба локальных указателя ушли, остаётся по 1 ссылке друг от друга: ни один узел не удалён
```

### Решение: weak_ptr

**`std::weak_ptr`** — наблюдатель: он получает доступ к тому же объекту, что и `shared_ptr`, но **не является владельцем** и не увеличивает счётчик ссылок. Если заменить один из указателей в цикле на `weak_ptr`, цикл разорвётся:

```cpp
struct test_class {
    std::weak_ptr<test_class> m_ptr;          // теперь не владеет
    ~test_class() { std::cout << "weak destructor called\n"; }
};

{
    auto ptr = std::make_shared<test_class>();
    ptr->m_ptr = ptr;
    std::cout << ptr.use_count() << "\n";     // Вывод: 1
}   // Вывод: weak destructor called — ресурсы освобождены
```

Для двух связанных узлов (родитель — потомок) правило такое: «сильной» ссылкой владеет тот, кто должен определять время жизни (обычно родитель), а обратная ссылка делается слабой.

### Как пользоваться weak_ptr

Напрямую `weak_ptr` разыменовать нельзя: объект, на который он смотрит, мог уже исчезнуть. Сначала его нужно превратить в `shared_ptr` методом `lock()` — он вернёт либо владеющий указатель, либо пустой, если объект уже удалён. Проверить это без блокировки можно через `expired()`.

```cpp
#include <iostream>
#include <memory>

struct node {
    int m_value;
    std::weak_ptr<node> parent;
    explicit node(int v) : m_value{v} {}
    ~node() { std::cout << "~node " << m_value << "\n"; }
};

int main() {
    {
        auto node1 = std::make_shared<node>(1);
        auto node2 = std::make_shared<node>(2);
        node1->parent = node2;
        node2->parent = node1;
        // node1->parent->m_value = 4;             // не скомпилируется
        node1->parent.lock()->m_value = 4;         // lock() даёт shared_ptr на node2
        std::cout << node2->m_value << " " << node1.use_count() << " " << node2.use_count() << "\n";
    }
    std::weak_ptr<int> w;
    {
        auto sp = std::make_shared<int>(5);
        w = sp;
        std::cout << "expired: " << w.expired() << "\n";
        if (auto s = w.lock()) std::cout << *s << "\n";
    }
    std::cout << "expired: " << w.expired() << " lock null: " << (w.lock() == nullptr) << "\n";
}
// Вывод:
// 4 1 1
// ~node 4
// ~node 1
// expired: 0
// 5
// expired: 1 lock null: 1
```

Оба узла уничтожены при выходе из блока (сначала `node2`, объявленный позже), а счётчики ссылок равны 1 — слабые ссылки их не увеличивают.

## Как выбрать

| Ситуация | Что использовать |
|---|---|
| Объект один владелец, создаётся и умирает вместе с ним | `unique_ptr` (по умолчанию) |
| Владельцев несколько, неизвестно, кто последний | `shared_ptr` |
| Нужна ссылка «посмотреть, если ещё жив», обратные ссылки, кэши | `weak_ptr` |
| Нужен просто доступ к объекту без владения | ссылка или сырой указатель (не владеющий) |

`unique_ptr` дешевле: у него нет счётчика и контрольного блока, а при необходимости его можно превратить в `shared_ptr` (`std::shared_ptr<T> s = std::move(u);`). Контейнеры с `unique_ptr` (`std::vector<std::unique_ptr<T>>`) разрешены, но их элементы можно только перемещать (см. [[06 STL часть 1]]).

## Частые ошибки

- Создавать несколько умных указателей из одного сырого (`unique_ptr` или `shared_ptr`) — двойное удаление.
- Вызывать `delete` для указателя, которым владеет умный указатель.
- Пытаться копировать `unique_ptr` вместо `std::move`.
- Использовать объект после `std::move(ptr)` — указатель пуст, обращение даст `nullptr`.
- Строить циклы из `shared_ptr` (родитель ↔ потомок, двусвязные структуры) — утечка памяти; разрывайте цикл через `weak_ptr`.
- Забывать виртуальный деструктор в базовом классе при хранении наследников через указатель на базу.
- Разыменовывать результат `lock()` без проверки на пустоту.

## Задачи для практики

1. Что выведет код `auto a = std::make_shared<int>(1); auto b = a; auto c = b; b.reset(); std::cout << a.use_count();`? Решение: `2` (остались `a` и `c`).
2. Перепишите функцию из раздела «Зачем это нужно» так, чтобы `delete[]` не требовался. Решение: `auto my_data = std::make_unique<int[]>(600);` — деструктор сработает на любом `return` и при исключении.
3. Двусвязный список из узлов `Node { std::shared_ptr<Node> next, prev; }` не освобождается. Почему и как исправить? Решение: `next` и `prev` образуют цикл; сделайте `prev` типа `std::weak_ptr<Node>`.

## Кратко (шпаргалка)

- Умные указатели = RAII для памяти в куче: деструктор освобождает ресурс.
- `auto_ptr` — не использовать; `unique_ptr` — один владелец, только `std::move`; `shared_ptr` — счётчик ссылок в контрольном блоке; `weak_ptr` — наблюдатель, доступ через `lock()`.
- Создавайте через `make_unique` / `make_shared`, а не через `new`.
- Не создавайте два умных указателя из одного сырого.
- Циклы из `shared_ptr` не освобождаются — разрывайте через `weak_ptr`.
